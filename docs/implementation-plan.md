## 3. 为什么先做玩法内核

概率、配额、材料、资源与胜负全部归纯规则 Module。三套风格共用相同规则与视图字段；网页和无界面模拟共用同一个 Interface。这样在美术待选时可以先检验整局是否合理，也避免 UI 动画时序误扣资源。

所有玩法路径都实现后再称内核完成：不能只做敲击动画而不做破碎、不能只做一轮而把商人/结算写成待办、不能用固定假数据代替实际升级影响。

## 6. 规则实现顺序与不变量

先构建值类型/常量/随机及只读视图，再做 strike / heat / deliver / recycle，再做原子结算、下一轮和终局，最后接商人、存档与会话。每步通过正式 Interface 验证，不将未经验证的临时捷径保留到最终代码。

必须持续保持：

- 每轮恰好三件；终结状态不回到 active；满阶、零热、无煤均有合法出口。
- 金币、废料、煤、完整度、印记不为负；印记不大于 3，升级不大于 2。
- 相同输入不修改旧对象；非法/重复动作不消费随机数、不加 revision。
- 每个合法击打只抽一次；预览/动画/取消不抽；主档恢复后不重抽。
- 交货、回收、破碎、商人扣款和日终惩罚恰好一次；不同来料不能复用旧件 id。
- 配额只算当轮实际交货，金币余额不是配额；废料从不计配额。
- 第 3/6/9 轮存活后才到商人；轮 12/印记耗尽不触发额外来访。
- 内核视图给出裂损与本次破碎两个概率，UI 不复制公式。

## 7. 平衡验证与玩法复核方法

至少使用 1000 个固定、公开可重放种子，记录策略、准确率模型和规则版本。基准策略为保守（先保当轮配额）、均衡（配额后考虑废料/升级）、激进（高阶/重锤）；另外运行空操作、只回收、低热盲敲、重复指令、只交原坯等滥用策略。

T06 将低/中/高建模为明确的松开时间偏差与随机失误比例，再通过正式时机判定获得实际精准/普通/偏击数量，避免固定精准比例掩盖锤柄和周期的作用。输入模拟拥有自己的种子流，不能消耗游戏 strike 流；详细参数见[模拟合同](simulation-contract.md)。对照项包括：通关率、失败轮次、达标轮数、总金币、废料消耗、破碎数、升级选择、每局击打数、每轮与胜利局有效输入时长。

R1 增加锤法专项对照：分别固定轻锤/标准锤/重锤与自适应选择，在相同种子和准确率模型下比较。精准时轻/标准每点进度热耗均为 4，重锤为 4.5；轻锤应力与风险较低，但需要更多次操作，因此存在高准确率下只用轻锤的支配风险。T06 必须报告这一项，连同操作次数/有效操作时长/破碎概率评价，不只证明“能通关”就放行。若其他锤法没有合理用途，先有据调整并同步设计/规格，不靠隐藏难度或只修改模拟器解决。

硬性验证：无操作/纯回收/只交原坯不能无代价通关；资源不能无限增长；相同动作回放完全一致；推进轮次的策略必须在有限步内结束。无操作停在首轮、不获利、不自动受罚，符合按操作轮次推进的设计，不凭空添加现实时间倒计时。至少存在按正式规则可重放的通关路径，不用测试入口改值。

玩法目标：中等操作的均衡策略应有可行的通关机会，高精准率要优于盲敲，前三轮比后三轮宽容，至少两种升级路线有明确用处。这些是要评价和迭代的假设，不把尚未实现的胜率目标写成通过。若所有策略后期都系统性失败，应先分析资源/风险/配额，再调数值并同步设计；不能只改模拟器造出好结果。

真人试玩观察：能否在一分钟内理解目标；能否解释裂损/破碎、交货/回收；是否主动收手；商人是否产生取舍；十二轮是否出现无聊重复或突然无解。无真人反馈时在报告中明确其证据缺失，自动化不冒充主观认可。

## 8. 图稿到正式界面的资产流程

T03 每个方向单独调用内置 imagegen；保留原图和完整 prompt，不以拼图代替三个独立方案。统一样例状态见 [UI 文档](ui-design.md)。主界面选定后以原图为风格参照，先派生整套设计稿，再输出适合代码拼装的背景和透明器具。

运行素材放 `public/assets/`，概念与提示词放 `design/`；不得只在 `$CODEX_HOME/generated_images/` 留一份。透明输出必须实际检查 alpha；不把棋盘格当透明、不切掉锤柄/工具边缘。资产清单记录 id、相对路径、尺寸、锚点、alpha、生成方式、来源图与用途。

背景不含交互文案；HUD 和数字全部代码渲染。铁件至少用形态/发光/纹理区分阶级，材料种类和裂损状态也要可辨；图标和简单几何可用代码绘制，不用模糊位图替代文字。画面要按同一坐标体系拼装，并在两个目标尺寸检查触点和轮廓。

## 9. 质量、安全与发布

浏览器验收按 [矩阵](acceptance-matrix.md) 保存实际结果、运行环境和截图。完整胜利/失败用正常点击/键盘操作走过每个阶段；可以用可控测试时钟稳定落锤，但不能注入高金币或终局状态来冒充一局。测试专用能力必须隔离在测试配置，生产构建不能暴露作弊按钮。

提交前检查源代码无未完成功能、敏感信息、临时生成器、测试报告或 node_modules；资产尺寸合理、来源清楚；依赖安装/审计错误有记录。若 CI 配置加入 GitHub，权限遵循最小化，构建不需要 secrets。运行时代码不读取 GitHub token。

本目标授权创建仓库、提交与推送，最终核对本地 HEAD 与远程 main 同 SHA、工作区干净。用户未要求具体在线托管，不擅自引入付费托管；静态构建、运行说明和 GitHub 源码是必要交付。有可访问部署才称上线。

## 10. 回滚与变更管理

逐任务提交，回滚用新 revert 提交，不强推。规则改动同步规则版本、数值表、测试和模拟报告；存档不兼容时保留原数据、解释版本问题，不能静默“修复”成另一局。艺术稿保留原候选与派生版本，不覆盖用户已选原图。

改变三件材料、轮次/胜负、核心操作或经济结构时必须回到原需求和设计说明影响，不用“优化”名义悄悄删功能。只是调参、修复或实现细节，在已经确认的方向内推进并保留证据。
